Login, Auth & Protected Routes in React

A step-by-step guide to building a React + TypeScript app with routing, email/password authentication using Firebase, login/logout and protected routes.

⚛️ React 19 🟦 TypeScript ⚡ Vite 🧭 React Router 🔥 Firebase Auth ⏱ ~45 min read

🧭 How to use this guide

  • Read it from top to bottom. Each section builds on the one before it.
  • Each section starts with what you'll learn and ends with key takeaways. Read the takeaways again before you move on.
  • Use the Copy button on any code block to copy the code.
  • In Section 10 you'll find an interactive simulator that shows what happens behind the scenes when you log in, log out and refresh.
  • Test yourself with the quiz at the end. The complete source code is in Appendix A.

Routing with React Router

You'll learn: how one HTML page can show different "pages" depending on the URL.

A single-page app (SPA) has only one HTML page. The router decides which component to show based on the URL, without reloading the page.

URL changes to /login→ Router finds the matching <Route>→ Renders <Login />→ No page reload ⚡

1. BrowserRouter: turns routing on

Wrap the app once, at the top. It watches the URL. Routes, Route, Link, Navigate and Outlet all need to be inside it.

2. Routes and Route: URL → component

path is the URL and element is what to render when it matches.

3. Link: navigate without reloading

<a href="/form"><Link to="/form">
Reloads the whole page?❌ Yes. The browser downloads everything again and React state is lost.✅ No. React only swaps the component.
Use forLinks to other websitesLinks inside your app

4. useNavigate: navigate from code

Use it when you need to redirect after something happens, such as a successful login. Link is for things the user clicks. useNavigate is for redirects in your own code.

ℹ️ Note All of these are imported from 'react-router-dom', for example import { Link, useNavigate } from 'react-router-dom'.

✅ Key takeaways

  • BrowserRouter wraps the app once. Routes/Route map URLs to components.
  • Use Link instead of <a> for internal links.
  • Use useNavigate() to redirect from code.

Firebase setup and environment variables

You'll learn: how to connect your code to Firebase and keep the config out of your source code.

.env→ import.meta.env→ firebaseConfig→ initializeApp()→ getAuth()→ export auth

firebase-config.ts

  • initializeApp connects your code to your Firebase project.
  • getAuth(app) gives you the auth object. You pass it to every Firebase auth function.
  • export lets other files import it with import { auth } from './firebase-config'.

.env: keeping config out of the code

  • Vite only exposes variables that start with VITE_.
  • Read them with import.meta.env.VITE_....
  • .env is listed in .gitignore, so it isn't committed. .env.example is committed as a template.
  • Restart npm run dev after changing .env.

A full .env.example looks like this (with empty values):

🔑 Are Firebase keys secret? No. Firebase web keys end up in the browser anyway. Real protection comes from Firebase security rules. The .env file keeps config out of git and lets you use different Firebase projects for different environments (for example development and production).
⚠️ Common mistake If the app says the API key is invalid or undefined, check that: (1) the variable name starts with VITE_, (2) .env is in the project root next to package.json, and (3) you restarted the dev server.

✅ Key takeaways

  • firebase-config.ts sets up Firebase once and exports auth.
  • Config values live in .env and must start with VITE_.
  • Restart the dev server after you edit .env.

Global state with Context (AuthContext)

You'll learn: how to share the logged-in user with every component, and how to write a custom hook. This is the most important section, so take your time.

The problem

Many components need to know who is logged in: the Navbar, the login page and the route guard. Passing user down through props at every level is tedious. This is called prop drilling. Context lets you share data with any component below it.

❌ Prop drilling

App owns user
↓ user
Layout doesn't need it, just passes it on
↓ user
Page passes it on again
↓ user
LogoutButton finally uses it

✅ Context

AuthProvider shares { user, signup, login, logout }
↓ any component below can read it directly ↓
NavbaruseAuth()
LoginuseAuth()
ProtectedRouteuseAuth()

The three pieces of Context

💡 Think of it like a radio createContext creates a radio channel. The Provider is the station that broadcasts a value. useContext is a radio that any component below the station can use to listen.

AuthProvider: the state and the Firebase logic

NameMeaning
userThe logged-in Firebase user, or null if nobody is logged in.
loadingtrue until Firebase tells us who is logged in.
childrenWhatever you put between the <AuthProvider> and </AuthProvider> tags.

Listening to login state

  • onAuthStateChanged runs the callback on page load and every time someone logs in or out.
  • useEffect with an empty array [] sets up the listener once, when the component first appears.
  • The returned unsubscribe function is the cleanup. It stops the listener when the component disappears.
  • Firebase remembers the session, so a page refresh keeps the user logged in.

The Firebase actions

These are thin wrappers around Firebase. They are async because they talk to a server and return Promises. If they fail, for example because of a wrong password, they throw an error. The component that calls them handles it (see Section 7).

🧠 Important You don't call setUser in these functions. When Firebase logs someone in or out, onAuthStateChanged fires and updates user for you. There is only one place that sets user.

Why wait for loading?

On page load, Firebase needs a moment to check the saved session. Without this line, user would be null for a split second, and a logged-in user would be redirected to /login on every refresh.

👉 You can try this yourself in the simulator: untick "Wait for loading", log in, go to Form and press refresh.

useAuth(): a convenient way to read the context

This is a custom hook: a function that wraps other hooks. Its name must start with use. It:

  • keeps AuthContext private, so components only import useAuth,
  • removes the null case, so TypeScript is happy and you don't need to check for null everywhere,
  • gives a clear error if you forget to wrap the app in AuthProvider.

✅ Key takeaways

  • Context avoids prop drilling: create it, provide it, then read it.
  • onAuthStateChanged is the single source of truth for user.
  • if (loading) return null prevents logged-in users from being bounced to /login on refresh.
  • Components use the custom hook useAuth(), never AuthContext directly.

Login and sign up form

You'll learn: controlled inputs, using one form for two jobs, async submit with error handling, and showing errors.

Controlled inputs

The input shows whatever is in state and updates the state on every keystroke. React is the single source of truth for the value.

User types "a"→ onChange fires→ setEmail('a')→ React re-renders→ input shows value={email}↻

Toggling between Log in and Sign up

One form handles both. The boolean decides the title, the button text and which function runs. type="button" stops this button from submitting the form. A button inside a form submits it by default.

Submitting

  1. e.preventDefault() stops the browser from reloading the page on submit.
  2. setError('') clears any old error message.
  3. await waits for Firebase. If Firebase throws, the catch block runs and shows an error.
  4. If nothing was thrown, navigate('/form') runs and takes the user to the protected page.
💡 Free validation Adding required and type="email" to the inputs makes the browser check them before handleSubmit even runs.

Showing the error

&& renders the paragraph only if error is not an empty string. An empty string is "falsy", so nothing is shown.

✅ Key takeaways

  • Controlled inputs: value comes from state and onChange updates state.
  • One boolean (isSignup) lets one form do two jobs.
  • Use try / catch around await to handle Firebase errors.
  • condition && <JSX /> renders something only when the condition is true.

Protected routes

Goal: only logged-in users can see /form.

User visits /form
↓
ProtectedRoute: is there a user?
↓ yes
<Outlet />renders <Form />
↓ no
<Navigate to="/login" replace />redirect to login

The guard (ProtectedRoute.tsx)

PieceWhat it does
<Navigate to="/login" />Redirects as soon as it is rendered.
replaceReplaces the current history entry instead of adding a new one. Without it, pressing Back would return to the protected page and bounce the user to /login again.
<Outlet />A placeholder for the child route. It renders the page that matched the URL.

Using it (App.tsx)

  • A Route with no path is a layout route. It doesn't match a URL itself. It just wraps its children.
  • When the URL is /form, React Router renders ProtectedRoute first. If the user is logged in, its <Outlet /> shows Form. Otherwise the user is redirected.

✅ Key takeaways

  • ProtectedRoute returns either <Navigate> (redirect) or <Outlet> (show the page).
  • Wrap protected routes in a layout route (a Route without a path).
  • Always use replace on redirects like this one.
  • Guards are for user experience. Security happens on the server.

How it all fits together

You'll learn: how all the pieces work together during page load, login, logout and when someone visits a protected page.

The component tree

  • BrowserRouterwatches the URL
    • AuthProviderholds user, loading, signup, login, logout
      • NavbaruseAuth() → user, logout
      • Routes
        • / → Home
        • /login → LoginuseAuth() → signup, login · useNavigate()
        • ProtectedRoutelayout route · useAuth() → user
          • /form → Formrendered by <Outlet />

Four scenarios, step by step

🔄 Page load

  1. AuthProvider starts listening with onAuthStateChanged.
  2. Firebase reports the saved user (or null), and loading becomes false.
  3. The app renders, and useAuth() returns the correct user.

🔓 Logging in

  1. The user submits the form, and login(email, password) calls Firebase.
  2. Firebase accepts it and onAuthStateChanged fires, so user is set.
  3. Everything that uses useAuth() re-renders. The Navbar shows "Log out" and ProtectedRoute lets /form through.
  4. navigate('/form') takes the user to the protected page.

🔒 Logging out

  1. The user clicks the logout button and signOut runs.
  2. onAuthStateChanged fires with null, and user becomes null.
  3. The Navbar shows "Log in", and ProtectedRoute redirects to /login the next time it renders.

🚫 Visiting /form while logged out

  1. ProtectedRoute sees user === null.
  2. It renders <Navigate to="/login" replace />.
  3. The user lands on the login page.

    Common questions

    Click a question to open the answer.

    Why TypeScript?
    It catches mistakes early (login(123) is an error because email must be a string), gives better autocomplete and documents the shape of your data. Vite supports plain JavaScript too, if you prefer.
    Do I need AuthContext if I use Firebase?
    Firebase handles authentication, but you still need a way to share the current user with your components. The context sets up one listener and shares the result everywhere.
    Why is useAuth() better than useContext(AuthContext)?
    It hides the context, removes the null check from every component and gives a helpful error when it's used outside the provider.
    Where does BrowserRouter go?
    Once, at the top of the app, above everything that uses routing.
    Is it safe to expose the Firebase API key?
    Yes. It identifies your project and is not a password. Control access with Firebase security rules and by restricting which domains are allowed to use the key in Google Cloud.
    Why do I get redirected to /login every time I refresh?
    You are probably rendering the routes before Firebase has finished checking the session. Make sure AuthProvider has if (loading) return null (see Section 6).

    Glossary

    Short definitions of the terms used in this guide.

    SPA
    Single-page application. One HTML page whose content JavaScript swaps out, without full page reloads.
    Component
    A function that returns JSX (UI). For example Navbar, Login or Home.
    Props
    Inputs passed to a component, like HTML attributes: <Route path="/" />. children is a special prop that holds whatever is between the tags.
    State (useState)
    Data a component remembers between renders. Changing it with the setter re-renders the component.
    Effect (useEffect)
    Code that runs after rendering, for example to set up a listener. It can return a cleanup function.
    Hook
    A function starting with use that gives components React features (useState, useEffect, useContext, useNavigate…).
    Custom hook
    Your own hook that wraps other hooks, like useAuth().
    Context
    A way to share a value with every component below a Provider, without passing props.
    Prop drilling
    Passing props through many components that don't need them, just to reach one that does.
    Provider
    The component (AuthContext.Provider) that supplies a context value to its children.
    Promise / async / await
    A Promise is a value that will arrive later. await pauses an async function until the Promise finishes. If it fails, an error is thrown.
    Controlled input
    An input whose value comes from React state and whose onChange updates that state.
    Conditional rendering
    Showing different JSX depending on a condition, using a ? b : c or a && b.
    Layout route
    A <Route> without a path that wraps child routes. Its <Outlet /> renders the matching child. This is how nested routes work.
    Environment variable
    A config value stored outside the code (in .env). In Vite it must start with VITE_ and is read with import.meta.env.
    Session
    Firebase remembers that a user is logged in (in the browser), so they stay logged in after a refresh.
    Security rules
    Rules on Firebase's servers that decide who can read or write data. This is the real protection, not the route guard.
